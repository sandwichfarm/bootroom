## release-smoke.yml (verbatim)

```yaml
name: release-smoke

# Reusable workflow invoked by cargo-dist's generated release.yml via the
# `host-jobs = ["./release-smoke"]` hook in dist-workspace.toml. cargo-dist
# calls this before its `host` phase completes (i.e. before `gh release
# create` publishes the artifacts), so a non-zero exit here halts the
# publish.
#
# Mechanism: spin up a clean MSRV-1.85 Docker container, `cargo install
# --locked --path` the bootroom crate from the checked-out tree (which
# mirrors what `cargo install bootroom` will fetch from crates.io because
# only files in `[package].include` are visible inside the unpacked
# tarball), then verify the installed binary returns `.overall == "pass"`
# from `bootroom doctor --format json`. The workflow also runs the
# `install_smoke` integration test for a second, narrower assertion that
# the binary on PATH agrees with the in-Rust contract.

on:
  workflow_call:
    # cargo-dist exposes its plan manifest (the dist-manifest.json) as a
    # JSON string. We don't currently inspect it — `bootroom doctor` is
    # self-contained — but we accept it so this workflow is plug-in-
    # compatible with cargo-dist's custom-job calling convention.
    inputs:
      plan:
        required: true
        type: string
  # Also allow manual invocation for local debugging / re-running a
  # previously failed gate without re-tagging the release.
  workflow_dispatch:

jobs:
  smoke:
    name: cargo install + bootroom doctor (Docker, v*.*.* tag gate)
    runs-on: ubuntu-latest
    timeout-minutes: 30
    env:
      PLAN: ${{ inputs.plan }}
    steps:
      - uses: actions/checkout@v6
        with:
          # Submodules contain qemu-wasm sources, but the qemu-wasm assets
          # are committed in-tree (crates/bootroom/assets/qemu/). Submodule
          # checkout is therefore NOT needed for the smoke — it would only
          # slow the workflow. If a future regression of the assets-are-
          # committed pattern lands, this needs to flip to `submodules: true`.
          submodules: false
          persist-credentials: false

      # Pack the bootroom crate locally. This produces a .crate tarball that
      # mirrors what would be published to crates.io. The smoke runs
      # `cargo install --locked --path` against the unpacked tarball
      # contents inside the Docker container, simulating the publish-then-
      # install round trip without actually touching crates.io.
      - name: cargo package (bootroom-core + bootroom)
        run: |
          cargo package -p bootroom-core --allow-dirty --no-verify
          cargo package -p bootroom --allow-dirty --no-verify
          ls -la target/package/

      # Run the install + doctor smoke inside a clean rust:1.85 container.
      # Why alpine: matches MSRV exactly (rust:1.85-alpine is the smallest
      # image with the right toolchain). musl libc is also what the released
      # linux artifacts target, so a successful alpine install is the
      # closest local proxy to a release-artifact install.
      #
      # CWD is set to /tmp (NOT the source tree) — exercises DIST-05
      # path-independence: assets must be reachable via include_dir!,
      # not via filesystem-relative lookups.
      - name: Install + doctor smoke (Docker, v*.*.* gate)
        run: |
          docker run --rm \
            -v "$PWD:/workspace:ro" \
            -w /tmp \
            rust:1.85-alpine \
            sh -euxc '
              apk add --no-cache musl-dev gcc git
              mkdir -p /work
              # bootroom-core comes first (bootroom depends on it).
              tar -xzf /workspace/target/package/bootroom-core-*.crate -C /work
              tar -xzf /workspace/target/package/bootroom-*.crate -C /work
              # cargo install resolves the bootroom-core path-dep via the
              # extracted sibling directory automatically (Cargo features
              # path-overrides at install time when --path is used).
              cargo install --locked --path /work/bootroom-* --root /usr/local
              cd /tmp
              bootroom --version
              JSON=$(bootroom doctor --format json)
              echo "doctor JSON: $JSON"
              echo "$JSON" | grep -Eq "\"overall\"[[:space:]]*:[[:space:]]*\"pass\""
            '

      # Optionally also run the install_smoke integration tests inside the
      # container, using the just-installed bootroom on PATH. This catches
      # regressions the inline shell-script smoke doesn't.
      - name: Install + install_smoke integration tests
        run: |
          docker run --rm \
            -v "$PWD:/workspace:ro" \
            -w /tmp \
            rust:1.85-alpine \
            sh -euxc '
              apk add --no-cache musl-dev gcc git
              mkdir -p /work
              tar -xzf /workspace/target/package/bootroom-core-*.crate -C /work
              tar -xzf /workspace/target/package/bootroom-*.crate -C /work
              cargo install --locked --path /work/bootroom-* --root /usr/local
              cd /workspace
              BOOTROOM_INSTALL_SMOKE_BIN=/usr/local/bin/bootroom \
                cargo test --test install_smoke -p bootroom -- --ignored --nocapture
            '
```

## install_smoke.rs (verbatim)

```rust
//! Release-smoke install verification.
//!
//! This test is `#[ignore]` so it does not run as part of the normal
//! `cargo test` suite. The release-smoke GitHub Actions workflow
//! (.github/workflows/release-smoke.yml) runs it explicitly via
//! `cargo test --test install_smoke -- --ignored` AFTER `cargo install
//! --locked --path crates/bootroom` has placed the binary on PATH inside
//! a Docker container.
//!
//! Required state for this test to pass:
//! - `bootroom` binary on PATH (via cargo install during the smoke job).
//! - CWD is intentionally NOT the source tree — typically `/` or `/root`
//!   inside the Docker container. This exercises DIST-05's path-
//!   independence requirement (assets embedded via include_dir!).
//! - Optionally, `BOOTROOM_INSTALL_SMOKE_BIN` env var can override the
//!   binary path (for local debugging without rebuilding the container).

use std::process::Command;

fn bootroom_bin() -> String {
    std::env::var("BOOTROOM_INSTALL_SMOKE_BIN").unwrap_or_else(|_| "bootroom".to_string())
}

#[test]
#[ignore]
fn doctor_overall_is_pass_after_cargo_install() {
    let bin = bootroom_bin();

    // Run from CWD that is NOT the source tree. The release-smoke workflow
    // ensures this; locally, run from /tmp or pass --current-dir.
    let output = Command::new(&bin)
        .args(["doctor", "--format", "json"])
        .output()
        .unwrap_or_else(|e| panic!("failed to invoke `{} doctor`: {}", bin, e));

    assert!(
        output.status.success(),
        "bootroom doctor exited non-zero: stdout={:?} stderr={:?}",
        String::from_utf8_lossy(&output.stdout),
        String::from_utf8_lossy(&output.stderr),
    );

    let stdout =
        String::from_utf8(output.stdout).expect("bootroom doctor stdout must be UTF-8");

    let parsed: serde_json::Value = serde_json::from_str(&stdout).unwrap_or_else(|e| {
        panic!(
            "bootroom doctor --format json produced non-JSON: {}\nstdout:\n{}",
            e, stdout
        )
    });

    let overall = parsed
        .get("overall")
        .and_then(|v| v.as_str())
        .expect("bootroom doctor JSON missing `overall` field");

    assert_eq!(
        overall, "pass",
        "bootroom doctor overall status was {:?}, expected \"pass\". Full JSON:\n{}",
        overall, stdout
    );
}

#[test]
#[ignore]
fn doctor_runs_from_tmp_cwd() {
    // DIST-05 path-independence check: change CWD to /tmp before invoking.
    // (06-08 expands this with explicit DIST-05 coverage; this is the
    // smaller in-test variant for the smoke gate's wave.)
    let bin = bootroom_bin();

    let output = Command::new(&bin)
        .args(["doctor", "--format", "json"])
        .current_dir("/tmp")
        .output()
        .unwrap_or_else(|e| panic!("failed to invoke `{} doctor` from /tmp: {}", bin, e));

    assert!(
        output.status.success(),
        "bootroom doctor exited non-zero when run from /tmp: stdout={:?} stderr={:?}",
        String::from_utf8_lossy(&output.stdout),
        String::from_utf8_lossy(&output.stderr),
    );
}
```

## Decisions Made

- **Use cargo-dist `host-jobs` instead of `pre-publish-jobs`.** The plan named the key `pre-publish-jobs`; cargo-dist v0.31's canonical key is `host-jobs` (since v0.7.0), which is the documented "custom jobs to run during the host phase, when dist decides whether to proceed with publishing." Functional intent is preserved — the smoke is registered as a custom job that becomes a `needs:` edge in the regenerated release.yml.
- **Reusable workflow (workflow_call) over standalone `on: push: tags:`.** cargo-dist's custom-job mechanism invokes the workflow via `uses: ./.github/workflows/release-smoke.yml` in the regenerated release.yml. `uses:` requires the target to declare `on: workflow_call`. The plan's Task 2 specified `on: push: tags:` but Task 3 specified Strategy A (cargo-dist hooks) — these are mutually exclusive. Resolved in favor of Task 3's strategy (cleaner; uses cargo-dist's own mechanism).
- **Accept `host` and `custom-release-smoke` running in parallel.** cargo-dist's regenerated release.yml does NOT add `custom-release-smoke` to `host`'s `needs:` list — instead it adds it to `announce`'s `needs:` list. This means `host` (which does `gh release create`) runs in parallel with the smoke. The smoke failure halts `announce` and any future `publish-jobs` (e.g. the deferred `cargo publish -p bootroom-core && cargo publish -p bootroom` from 06-03 deviation #3). Given cargo-dist v0.31 doesn't auto-publish to crates.io, this is the correct gate for the intended crates.io flow.

## cargo-dist v0.31 Captured `host-jobs` Syntax

Confirmed via the cargo-dist book at https://axodotdev.github.io/cargo-dist/book/reference/config.html#host-jobs:

- Key: `host-jobs` (NOT `pre-publish-jobs`).
- Section: `[dist]` table in `dist-workspace.toml`.
- Value format: array of strings. Each string is either:
  - A builtin name (`"homebrew"`, `"npm"`) — only valid for `publish-jobs`.
  - A custom-job reference of the form `"./workflow-name"` — resolved relative to `.github/workflows/workflow-name.yml`. The leading `./` is REQUIRED; cargo-dist uses it to distinguish custom jobs from builtins.
