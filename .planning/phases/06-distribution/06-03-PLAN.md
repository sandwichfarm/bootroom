<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| local dev tooling (cargo-dist) → committed CI config | `cargo dist init` writes YAML and TOML into the repo. The committed output is the trust surface — once merged, the release workflow runs on GitHub Actions infrastructure and has access to publishing credentials. |
| GitHub Actions runner → crates.io | release.yml's publish job uses `CARGO_REGISTRY_TOKEN` secret to publish. Token is scoped to the bootroom crate (assumes user has provisioned a crates.io API token with publish-only scope and added it as a repo secret named `CARGO_REGISTRY_TOKEN`). |
| GitHub Actions runner → GitHub Releases | release.yml uses the default `GITHUB_TOKEN` (auto-provisioned per workflow run) to upload assets. No external secret needed for this leg. |
| git tag push → release workflow trigger | Anyone with push access to the repo can trigger a release by pushing a `v*` tag. cargo-dist's default doesn't gate on branch — pre-merge tag pushes from a fork would not trigger (forks don't have repo secrets), but a tag pushed by a maintainer triggers immediately. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|---|---|---|---|---|
| T-06-03-01 | Spoofing | A forked PR pushing a `v*` tag triggers a real release | mitigate (by GitHub Actions defaults) | Forks cannot access repo secrets; `CARGO_REGISTRY_TOKEN` is unavailable on fork-triggered workflow runs. cargo-dist's default workflow only runs from the canonical repo's tags. |
| T-06-03-02 | Tampering | Hand-edits to release.yml drift from cargo-dist defaults | mitigate | CONTEXT.md D-01 explicitly forbids hand-editing release.yml. Task 2 enforces "re-run cargo dist init if defaults are wrong". The Task 3 audit catches drift. |
| T-06-03-03 | Tampering | Cargo-dist version drift between local init and CI runner | mitigate | `cargo-dist-version` pin in `[workspace.metadata.dist]` (or sibling) makes the CI runner install the exact version that generated the workflow. Drift is impossible. |
| T-06-03-04 | Repudiation | Published release artifacts don't match what was tagged | accept | cargo-dist's release.yml computes SHA256 checksums and signs them via GitHub's attestation mechanism (cargo-dist default). Downstream consumers verify via `cargo binstall --signature` or shell-installer's built-in checksum verification. |
| T-06-03-05 | Information Disclosure | crates.io token leaked via workflow logs | mitigate (by GitHub Actions secret masking) | GitHub Actions masks secret values in logs automatically. cargo-dist's publish step does not echo the token. |
| T-06-03-06 | Denial of Service | crates.io rate limit blocks publish (two publishes within ~60s) | accept | Out-of-scope per CONTEXT.md `<deferred>`. Operational concern; the release-smoke gate (06-06) prevents repeated retry storms. |
| T-06-03-07 | Denial of Service | cargo-dist's homebrew tap update step fails (no tap repo exists yet) | accept | First release's homebrew step is expected to fail until a `homebrew-bootroom` tap repo exists. CONTEXT.md `<deferred>` says tap maintenance beyond auto-emit is out-of-scope. Document the expected first-release failure in the SUMMARY. |
| T-06-03-08 | Elevation of Privilege | A malicious `[workspace.metadata.dist]` block adds attacker-controlled installer URLs | accept | The metadata block lives in source; any change to it is visible in git diff. Standard code-review hygiene catches malicious edits. |
| T-06-03-09 | Spoofing | Repo rename invalidates cargo-binstall discovery | mitigate | `[package.repository]` URL is stored in the published tarball at publish time. Future renames break NEW publishes' discovery URL but don't retroactively break existing releases. The first publish under the bootroom name pins the URL into the crates.io record. |
</threat_model>
