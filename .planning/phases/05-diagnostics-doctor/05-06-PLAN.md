Current Cmd variants (after 05-03):
- `Cmd::Serve(ServeArgs)` — has doc-string (added Phase 1)
- `Cmd::Run(RunArgs)` — has doc-string `/// Run a scenario headlessly under Chromium and exit with a CI-style ...` (Phase 4)
- `Cmd::Check(CheckArgs)` — doc-string from Phase 3
- `Cmd::Init(InitArgs)` — doc-string from Phase 3
- `Cmd::Doctor(DoctorArgs)` — doc-string from 05-03 (`/// Run preflight checks (version, browser, headers, config).`)

Target text shape (single declarative sentence ≤80 chars):
- Serve  → `/// Serve the harness over HTTP for a real browser tab.` (or similar — preserve Phase-1 intent)
- Run    → `/// Run a scenario headlessly under Chromium and exit 0/1 on serial assertions.`
- Check  → `/// Validate a bootroom.toml without starting the server.`
- Init   → `/// Write a minimal example bootroom.toml to the current directory.`
- Doctor → `/// Run preflight checks (version, browser, headers, config).`

Long-form `///` paragraphs (rendered in `bootroom <sub> --help`) are fine and encouraged where they add operational context. The audit is on FIRST LINE only.

clap-derive contract (per Research Pitfall 9):
- First line of `///` → clap's `about` (one-line help text on `bootroom --help`)
- Subsequent lines → clap's `long_about` (full help text on `bootroom <sub> --help`)
- A first line >80 chars wraps badly in the subcommand list.

The five-name pin test must NOT use position-based string parsing of `--help` output (clap formatting is allowed to change between minor releases). Instead, assert all five names appear AT ALL, and that no surprise sixth subcommand appears. A reasonable shape:

```rust
let stdout = String::from_utf8_lossy(&output.stdout);
let expected = ["serve", "run", "check", "init", "doctor"];
for name in expected {
    assert!(stdout.contains(&format!("\n  {name} ")) || stdout.contains(&format!("\n  {name}\n")),
        "subcommand '{name}' missing from --help output:\n{stdout}");
}
// Catch the inverse: any surprise subcommand
let known = ["serve", "run", "check", "init", "doctor", "help"]; // clap auto-adds `help`
// Parse clap's "Commands:" section and assert every listed command is in `known`.
```

Adjust the leading-whitespace shape to match clap 4.x's actual formatting; verify by running `bootroom --help` once and copying the indent verbatim.

  <files>crates/bootroom/src/cli.rs</files>
  <action>Read the current `cli.rs` `Cmd` enum and the five `*Args` structs (`ServeArgs`, `RunArgs`, `CheckArgs`, `InitArgs`, `DoctorArgs`, plus `CommonArgs`). For each:

1. **First line of `///` ≤ 80 chars.** Count visible chars (excluding the `/// ` prefix). If a first line exceeds 80 chars or wraps to a second line in the source for stylistic reasons, rewrite it as one declarative sentence ≤80 chars.

2. **First line is declarative.** Form: imperative or noun-phrase describing what the subcommand DOES, not what it IS. Good: "Serve the harness over HTTP for a real browser tab." Bad: "This is the serve command."

3. **No internal jargon in the first line.** "MTTCG", "PTY", "xterm-pty slave" belong in long_about paragraphs, not in `bootroom --help`. The first line is the elevator pitch.

4. **Per-flag doc-strings on `*Args` public fields.** Every `pub field` annotated with `#[arg(...)]` should have a `///` doc-string. clap derive renders these as the flag's `--help` text. Audit each Args struct; add doc-strings where missing. Existing doc-strings: leave alone unless they violate constraint 1 or 3.

5. **Preserve existing variant ordering.** Doctor stays last. Serve stays first. Etc.

Do NOT change:
- Variant names
- Field names
- Field types
- `#[arg(...)]` attributes (long names, short flags, value_enum bindings, default_value_t bindings)
- The `///` doc-strings on internal-only structs (e.g. `Cli` itself) unless they're broken too

Run `cargo run -p bootroom -- --help`, `cargo run -p bootroom -- serve --help`, etc., for each subcommand and visually confirm the output is clean and one-line-per-subcommand at the top level.

After this audit, all five subcommands in `--help` MUST render on one line each, with their first-line doc-string fitting cleanly in the column clap allocates.

  <action>Add ONE new `#[test]` function to the existing `crates/bootroom/tests/cli_subcommands.rs`. Do NOT remove or modify existing tests.

Test name: `top_level_help_lists_exactly_five_subcommands`

Test body:
1. Invoke `Command::new(env!("CARGO_BIN_EXE_bootroom")).arg("--help").output()`.
2. Assert exit status is 0.
3. Decode stdout as `String::from_utf8_lossy`.
4. For each of `["serve", "run", "check", "init", "doctor"]`: assert the output contains the name on a line that follows clap's "Commands:" section. The simplest robust check: extract the lines between the `Commands:` header and the next blank line, then for each expected name assert `command_block.contains(name)`. Allow `help` as a sixth auto-added entry (clap-derived).

5. Inverse pin: extract all command names from the Commands block (use a regex like `^  (\w+)` on each indented line); assert that the set of extracted names is a subset of `{serve, run, check, init, doctor, help}`. If any other name appears (e.g., a partially-merged feature flag accidentally added a command), fail with a clear message naming the surprise.

6. Order assertion (optional but cheap): assert the indices of the five known names within the Commands block follow the documented order (`serve < run < check < init < doctor`). Use `find()` on each name; sort indices; compare to ascending sorted form.

Use the same `bootroom_bin()` resolver pattern as 05-05 if present in the file already; otherwise inline `env!("CARGO_BIN_EXE_bootroom")`.

This test catches three regression classes at once:
- Subcommand deletion (one of the five names disappears)
- Subcommand rename (one of the five names changes; the inverse pin catches a new name; the forward pin catches the absence of the old)
- Subcommand surprise addition (a sixth subcommand sneaks in via a feature flag toggle — the inverse pin catches this)

Run `cargo test -p bootroom --test cli_subcommands` to verify GREEN.</action>
