<interfaces>
Tests run the compiled bootroom binary via `std::process::Command`. The bootroom test crate already has a pattern for resolving the binary path via cargo (see `tests/check_subcommand.rs` / `tests/init_subcommand.rs` for examples — they use `env!("CARGO_BIN_EXE_bootroom")` directly).

Canonical pattern (mirrors `init_subcommand.rs`):
```rust
fn bootroom_bin() -> &'static str {
    env!("CARGO_BIN_EXE_bootroom")
}

let output = std::process::Command::new(bootroom_bin())
    .args(["doctor", "--format", "json"])
    .output()
    .expect("running bootroom doctor should succeed");
```

For `check_headers` to be callable from an integration test, expose it (or a thin async wrapper) from `lib.rs`. Cleanest: in 05-04, declare `pub mod doctor_cmd;` (already done by 05-03). In this plan, if `check_headers` is private to doctor_cmd.rs, add `pub(crate) async fn check_headers()` and re-export via lib.rs's `pub mod doctor_cmd;` (integration tests live OUTSIDE the crate so they need `pub`, not `pub(crate)`). Two acceptable options:

OPTION A (preferred): change `check_headers` from private `async fn` to `pub async fn check_headers() -> Check` and re-export `Check` and `CheckStatus` from the module as `pub`. Integration tests then call `bootroom::doctor_cmd::check_headers().await` directly.

OPTION B: keep doctor_cmd internals private; the integration test for headers calls the binary as a subprocess and inspects the JSON output looking for the `headers` check entry. Slightly noisier but no visibility changes.

Recommendation: OPTION A — exposing `Check` / `CheckStatus` / `check_headers` is reasonable for a doctor module, and several tests benefit. If the executor disagrees, OPTION B is acceptable; document the choice in the SUMMARY.
