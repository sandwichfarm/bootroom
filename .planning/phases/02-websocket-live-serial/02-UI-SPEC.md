# Phase 2 — UI Design Contract

> Visual and interaction contract for Phase 2 (WebSocket + Live Serial) of bootroom.
> Generated by gsd-ui-researcher; verified by gsd-ui-checker.
>
> **This spec INHERITS from `.planning/phases/01-walking-skeleton/01-UI-SPEC.md` (approved 2026-05-17).** Phase 1's design system, palette, spacing scale, typography roles, copywriting tone, accessibility floor, and component inventory remain authoritative. **This document records only the diff.** Where this spec is silent, Phase 1 governs.

**Phase scope reminder (from `02-CONTEXT.md` `<domain>`):** add Launch + Reset buttons (full page-reload semantics in Phase 2), Clear + Copy controls scoped to the terminal frame, a new `Idle` status pill state, and live keyboard input (Phase 1's `attachCustomKeyEventHandler(() => false)` is removed). The `/ws` endpoint, write funnel, and pacing logic are implementation concerns of the planner/executor and do not surface new visual elements beyond what is described here.

**Aesthetic anchor (unchanged from Phase 1):** developer test harness, terminal-adjacent, dense, no chrome. GDB web UI / Buildbot console — *not* a SaaS dashboard. Buttons that ship in this phase must read as *part of the header strip*, not as marketing CTAs.

## Design System

Unchanged from Phase 1.

| Property | Value | Change |
|----------|-------|--------|
| Tool | none | unchanged |
| Preset | not applicable (vanilla HTML + ES modules; project constraint forbids npm/bundler) | unchanged |
| Component library | none (hand-authored HTML, single `style.css`) | unchanged |
| Icon library | none — Phase 2 introduces **two** controls (Clear, Copy) that would conventionally be iconified; per the no-icon-library policy and the "≤4 components" target, **they ship as text labels in the existing monospace font**, not glyphs/SVGs. Rationale below. | clarified |
| Font | System monospace stack (see Phase 1) | unchanged |

**Icon-library rationale (Phase 2):** Vendoring an icon font or SVG sprite for two terminal controls is a poor tradeoff against the project's no-npm + minimal-footprint posture. Unicode box-drawing or symbol characters (e.g. `⌫`, `⎘`) introduce font-metric inconsistency across system monospace fallbacks. Text labels in the existing monospace stack are zero-dependency, screen-reader friendly, and visually consistent with the `LAUNCH` / `RESET` buttons that ship in the same phase.

### Idle pill color decision

**Decision: `Idle` reuses `--fg-muted` (`#7A8295`) — no new palette entry.**

Rationale:
- Adding `--status-idle` would expand the palette from 6 to 7 color tokens for one state that exists only between page load and first `Module.onRuntimeInitialized` callback (typically <100ms).
- `--fg-muted` is semantically correct: "no signal yet" reads as a muted/neutral state, parallel to how muted-foreground signals "not the headline value" elsewhere in the header.
- The `--status-idle` alternative was considered (per scope-reminder) but rejected because the palette is already terse on purpose — the project tolerates one shared muted color across "label" and "no-state-yet" surfaces.
- Contrast: `#7A8295` background under `#0E1116` text on the pill — verify with a contrast checker at executor time. If contrast fails (likely, since the pill flips fg/bg vs body text), use `#C0CAF5` (`--fg`) as the text color on the muted pill background (same fg/bg inversion the running/loading/halted pills use). The executor must verify the chosen text color reaches WCAG AA (4.5:1) on the muted background.

### Accent reservation (strict, per Phase 1 contract)

Accent (`--accent`) is reserved EXCLUSIVELY for:
1. The "bootroom" wordmark (header, top-left).
2. The `sha256` field value (12-char prefix in the header).
3. **NEW in Phase 2:** the 1px focus ring on Launch/Reset/Clear/Copy when `:focus-visible` is active. Focus rings are an accessibility floor — they are visible only during keyboard navigation and never as resting decoration.

Specifically NOT used for: button fill, button text, button hover state, status pills (each has its own semantic), or any other surface introduced in this phase.

### Button hover state (new)

Hover state for Launch/Reset/Clear/Copy is a **slight surface lift, no color change**:
- Resting: `background: var(--surface)` (`#1A1F26`)
- Hover: `background: var(--surface)` + a 1px inset top border in `var(--fg-muted)` (`#7A8295`), simulating a "raised" effect with palette colors only.
- Active (mousedown): same as resting (no further depression visual — terminal aesthetic is flat).
- Focus-visible: 1px outline in `var(--accent)`, `outline-offset: 1px`.
- Disabled: text color shifts to `var(--fg-muted)`, background stays at `var(--surface)`, cursor: `not-allowed`.

No `transition` on color/background — terminal feel is immediate, not animated.

## Interaction Contracts (Phase 2)

Phase 1's five interaction contracts remain. Phase 2 adds the following and amends two:

### Amended from Phase 1

- **(amend) xterm.js mount — keyboard is now live.** Phase 1's `attachCustomKeyEventHandler(() => false)` is removed. `xterm.onData(bytes => funnel.enqueue(bytes, { pacingMs: 0 }))` is added. The funnel writes to `slave.write` so the existing xterm-pty wiring carries bytes to the guest. The Phase 1 comment marking input as a stub MUST be removed in the same commit.
- **(amend) emscripten lifecycle → status pill.** Phase 1's three transitions (LOADING → RUNNING → HALTED) become four. The new initial state is `IDLE`, present before xterm and qemu have started initializing. See state machine below.

### New in Phase 2

1. **Status pill state machine (per `02-CONTEXT.md` `<decisions>` "Browser auto-open + status pill source"):**
   | State | Trigger |
   |-------|---------|
   | `IDLE` | Initial state on page load, before any qemu init has begun. JS sets this synchronously when the module script runs (replacing the static `data-state="LOADING"` Phase 1 sets in HTML). |
   | `LOADING` | After xterm mount completes, before `Module.onRuntimeInitialized` fires. |
   | `RUNNING` | `Module.onRuntimeInitialized` fired AND first `SerialOut` byte received (Phase 2 raises the bar from Phase 1's "init only" — RUNNING now means the guest is actually executing). |
   | `HALTED` | `Module.onExit` OR `Module.onAbort` OR WS `State { state: Halted }` from server. |
   - **WS authority:** when `/ws` is connected, server-pushed `State` messages override the locally-derived state. Local state-machine logic still runs but defers to the most recent WS `State`.
   - **Reconnection:** while `/ws` is reconnecting, the pill keeps the most recent state — no special "RECONNECTING" pill state (logged into terminal instead, per Copywriting).
2. **Launch button click handler.** Sequence:
   1. Set both buttons `disabled`.
   2. Send `WsMessage::Launch` over `/ws` (best-effort; if WS is closed, log to terminal and proceed).
   3. After a `tick` (≤16ms `requestAnimationFrame`) call `window.location.reload()`.
   3. Buttons remain disabled until the page unloads — no need to re-enable.
3. **Reset button click handler.** Identical to Launch, sending `WsMessage::Reset` instead. (Phase 2 intentionally makes the two visually distinct but behaviorally identical, per `02-CONTEXT.md`.)
4. **Clear button click handler.** Calls `xterm.clear()`. No WS traffic generated. No status pill change.
5. **Copy button click handler.**
   1. Read `xterm.getSelection()`; if empty, read full buffer via `xterm.buffer.active.translateToString(true, 0, xterm.buffer.active.length)`.
   2. `navigator.clipboard.writeText(text)`.
   3. On success: label → `COPIED` for 1500ms, then revert.
   4. On failure: label → `COPY FAILED` for 1500ms, then revert; write `[bootroom] Copy failed: <reason>` into the terminal via `slave.write` so the failure is auditable.
6. **`/ws` connection lifecycle.**
   - Connection opens on page load (after xterm is mounted; before `bootGuest()`).
   - On `Hello { version }`: validate version compatibility; mismatch logs to terminal but does not block.
   - On `SerialIn { data }`: base64-decode and enqueue via the write funnel with the configured pacing.
   - On `State { state }`: update status pill (overrides local lifecycle).
   - On disconnect: log to terminal, attempt naive reconnect (simple retry loop — no exponential backoff in Phase 2 per `<deferred>` ideas). Buttons stay enabled — Launch/Reset are still meaningful even with WS down (they reload the page).
7. **SerialOut mirror.** xterm-pty's `slave.onReadable()` → drain → emit `WsMessage::SerialOut { data: btoa(bytes) }` over WS (batched per readable burst).
8. **Keyboard focus management.** Clicking anywhere inside `#terminal` focuses xterm (xterm's default behavior). The Launch / Reset / Clear / Copy buttons are reachable by Tab; the focus ring (accent, 1px) makes them visible. No focus-trap; no auto-focus on page load.

### Explicitly NOT in Phase 2

- No confirmation dialog before Launch/Reset (terminal aesthetic; reload is a known cost).
- No keyboard shortcut for Clear/Copy (Phase 2 — may revisit if friction reported).
- No in-place qemu reset (deferred per `02-CONTEXT.md` `<deferred>`).
- No tooltips on buttons (label is the tooltip; mono labels are unambiguous).
- No transition animations on button hover/focus (terminal feel is flat).
- No exponential-backoff WS reconnect (deferred).
- No multi-tab support; one connection per page.

## Accessibility Floor (Phase 2 deltas)

Phase 1's contract holds. Additions:

- All four new buttons are real `<button>` elements with text labels (no icon-only buttons; no `aria-label` shenanigans required because the visible text IS the accessible name).
- `:focus-visible` outline uses `--accent` at 1px — visible during keyboard navigation, suppressed during mouse use (per browser default behavior of `:focus-visible`).
- Disabled state uses `disabled` attribute (not just CSS) so assistive tech announces the button as disabled.
- The `Idle` pill text reads aloud as "IDLE" (real text, same pattern as Phase 1 — color is not the sole carrier of state).
- The COPIED / COPY FAILED transient labels live in the same DOM element as `COPY`; screen readers will announce them as the label changes. No `aria-live` region needed (the change IS the feedback).
- Contrast verification (executor must validate at implementation):
  - Button text `var(--fg)` (`#C0CAF5`) on `var(--surface)` (`#1A1F26`) — must reach WCAG AA 4.5:1 (expected; Phase 1 already uses this pair on header text).
  - Disabled button text `var(--fg-muted)` (`#7A8295`) on `var(--surface)` — passes AA per Phase 1 verification (5.6:1 on `--bg`; verify it still passes on `--surface` since surface is slightly lighter).
  - Idle pill text on `var(--fg-muted)` background — see Color section (executor must verify and pick `--bg` or `--fg` as text color).
  - Accent focus ring at 1px against `var(--surface)` button — verify visibility; accent on bg passes 8.0:1, on surface should be ≈7.0:1.
- xterm's default keyboard handling now reaches the guest. xterm.js's accessibility tree (screen-reader live region for terminal output) is whatever 5.3.0 ships — bootroom does not regress it and does not configure `screenReaderMode` differently from Phase 1.
