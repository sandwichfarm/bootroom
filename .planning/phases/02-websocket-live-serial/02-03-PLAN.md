<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI argv → bootroom process | clap parses untrusted argv (e.g. `--host`, `--port`, `--kernel`); already validated in Phase 1 (kernel existence, IpAddr parsing). `--no-open` is a bool — no parsing surface. |
| bootroom → OS shell (via `open::that_detached`) | The URL constructed for `open::that_detached` is built server-side from `listener.local_addr()`; no user-controlled string is interpolated. `open::that_detached` does NOT invoke a shell — it spawns a process. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-04 | Injection | URL passed to `open::that_detached` | mitigate | URL is `format!("http://{bound}")` where `bound: SocketAddr`. `SocketAddr::Display` cannot produce shell metacharacters; `open` does not invoke a shell anyway. No interpolation of user-supplied strings into the URL. |
| T-02-05 | Denial of Service | `open::that_detached` blocks the parent process | mitigate | `that_detached` spawns the child detached (per `open` crate 5.x docs). If it returned an error (no launcher found), we log a warning and continue serving — failure does NOT abort the server. |
| T-02-06 | Spoofing | A local attacker tricks the user's `xdg-open` to launch a different browser | accept | bootroom runs on loopback only (Phase 1 default). The attacker must already have local code execution to modify `xdg-open` behavior — at which point bootroom is not the relevant attack surface. Out of Phase 2 scope. |
| T-02-07 | Information Disclosure | Server prints `bound` (local socket address) to stdout | accept | The address is intended to be visible — it is the URL the user opens. Loopback by default. |
</threat_model>
