       ```javascript
       function connectWs() {
         const url = `${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}/ws`;
         ws = new WebSocket(url);
         ws.onopen = () => { /* nothing — first frame is Hello, handled below */ };
         ws.onmessage = (ev) => {
           let frame;
           try { frame = JSON.parse(ev.data); }
           catch (e) { console.warn('[bootroom] /ws: bad JSON:', e); return; }
           handleWsFrame(frame);
         };
         ws.onclose = () => {
           try { slave.write('[bootroom] /ws disconnected; reconnecting…\r\n'); } catch (_e) {}
           setTimeout(connectWs, 1000);  // naive retry per <deferred>
         };
         ws.onerror = (e) => { console.warn('[bootroom] /ws error:', e); };
       }
       ```

    4. Frame dispatcher:
       ```javascript
       function handleWsFrame(frame) {
         if (!frame || typeof frame.type !== 'string') return;
         switch (frame.type) {
           case 'Hello':
             // Validate version compatibility (log mismatch; do not block).
             // Hard-coded client expected = the bootroom binary's CARGO_PKG_VERSION
             // is not exposed to the browser — instead, we just log whatever
             // the server reports and accept it. UI-SPEC Copywriting line 136.
             try { slave.write('[bootroom] /ws connected (server version ' + (frame.version || 'unknown') + ')\r\n'); } catch (_e) {}
             // Note: a future tightening could ship CARGO_PKG_VERSION into the page
             // via a meta tag for version-mismatch warnings. Phase 6 may revisit.
             break;
           case 'SerialIn':
             try {
               const bytes = b64ToBytes(frame.data || '');
               funnel.enqueue(bytes, { pacingMs });
             } catch (e) {
               console.warn('[bootroom] /ws SerialIn decode failed:', e);
             }
             break;
           case 'State':
             if (typeof frame.state === 'string') {
               serverStateAuthority = frame.state.toUpperCase();
               setPill(serverStateAuthority);
             }
             break;
           default:
             console.debug('[bootroom] /ws: unhandled frame type', frame.type);
         }
       }
       ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User keyboard → xterm → `keyEventToBytes` → funnel → slave | Same-origin user input; KeyboardEvent is browser-trusted. The byte translation table is fixed. |
| WS server `/ws` → browser onmessage → `JSON.parse` → `handleWsFrame` | Same-origin loopback. JSON is parsed via the standard browser API (no eval). Frame fields are pattern-matched and ignored if unknown. |
| Browser `bytesToB64` → ws.send → server log | Bytes originate from `slave.read()` (guest serial output); on the wire as base64 strings. |
| `navigator.clipboard.writeText` → OS clipboard | Browser permission-gated; failure mode (denied / not-available) is surfaced to the user via the COPY FAILED label + terminal log line. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-22 | Tampering | A malicious page in another tab cannot reach this page's `funnel` because there's no postMessage receiver and no cross-origin script | mitigate | Single-tab single-origin design. No `window.addEventListener('message')` in app.js. Funnel is module-scoped to app.js; not exposed on `window`. |
| T-02-23 | Information Disclosure | clipboard contents readable by any JS on the page after `navigator.clipboard.writeText` | accept | bootroom is single-origin loopback; only its own code runs. The clipboard write is user-initiated by the COPY click (gesture-gated by browser). No additional read of the clipboard occurs. |
| T-02-24 | Denial of Service | Malformed WS Hello / State / SerialIn frames cause the handler to throw and break onmessage | mitigate | `handleWsFrame` wraps each branch in try/catch; unknown frame types log to console.debug. No throws propagate to the WebSocket event loop. |
| T-02-25 | Denial of Service | Naive WS reconnect (`setTimeout(connectWs, 1000)`) becomes a tight loop if the server hard-rejects every connect attempt | accept | Per 02-CONTEXT.md `<deferred>`: exponential backoff is explicitly out of scope for Phase 2. 1-second steady-state retry is acceptable on a loopback dev tool (a wedged server is a developer-attention issue). Phase 3+ may revisit. |
| T-02-26 | Tampering | Funnel byte order can be corrupted if a synchronous re-entrant enqueue occurs during `slave.write` | mitigate | The funnel's `draining` flag (plan 04 Pitfall #7 fix) serializes the drain loop; concurrent enqueues append to the queue and the in-flight drain picks them up in order. Verified by inline manual test plan (plan 04). |
| T-02-27 | Information Disclosure | Hello.version is shown in the terminal | accept | bootroom is loopback-only; the user already trusts the server. |
| T-02-28 | Tampering | LAUNCH / RESET buttons trigger page reload, which any visited page on the same origin can also trigger | accept | Loopback single-origin; no XSS surface; no postMessage receiver. Reload is a normal browser primitive. |
| T-02-29 | UI Spoofing | COPY FAILED label could mislead users into thinking the copy succeeded | mitigate | The label change is paired with a `[bootroom] Copy failed: <reason>` line written into the terminal so the failure leaves an audit trail (per 02-UI-SPEC Copywriting Contract line 138). |
</threat_model>
