<objective>
Create the load-bearing browser-side single-writer funnel. This module is the WS-02 mitigation: by being the sole caller of `slave.write` (and by virtue of plan 06 removing all other call sites), it guarantees no interleaving between user keystrokes and WS-arriving `SerialIn` scenario bytes. WS-03 inter-character pacing is a per-enqueue option.

Purpose: WS-02 (single-writer guarantee) + WS-03 (pacing). The funnel exists purely to enforce the invariant; the math is trivial; the structure is the whole point.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `Funnel.enqueue` argument | Bytes come from two trusted-within-browser sources: (1) `xterm.attachCustomKeyEventHandler` translating user KeyboardEvents (origin: same-document); (2) WS `SerialIn` frames after base64 decode (origin: same-host loopback `/ws`). Neither is untrusted in the Phase 2 threat model (bootroom is loopback-only per PROJECT.md). |
| `bytesToB64` / `b64ToBytes` | Pure functions over byte arrays / strings; no side effects, no I/O. |
| `keyEventToBytes` | KeyboardEvent comes from user input on the same origin. No untrusted input crosses this boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-08 | Denial of Service | Unbounded growth of `this.queue` from runaway WS SerialIn enqueue burst | accept | Phase 2 server is a pass-through observer; no scenario engine yet. The mpsc cap on the server side (32 frames, plan 02) is the upstream throttle. Phase 4 will add `--max-bytes-per-action` enforcement at the scenario engine. |
| T-02-09 | Tampering | Caller writes to `funnel.queue` or `funnel.draining` directly to break the invariant | accept | JS has no enforceable private fields beyond `#name` syntax (which `#drain` uses). The `queue` and `draining` fields are conventionally-public. Defense-in-depth comment in JSDoc warns "do not mutate these fields directly." Loopback dev tool; no adversarial caller. |
| T-02-10 | Information Disclosure | base64 of serial bytes ends up in DevTools network pane | accept | The serial bytes ARE the user-visible terminal contents. Disclosure to the same user via DevTools is not a confidentiality issue. |
