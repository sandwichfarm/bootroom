<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| broadcast::Receiver → per-conn mpsc::Sender → WS sink | Three tokio tasks per connection; each owns its own slice of the lifecycle. |
| WS frame flooding amplification | The forwarder reads from the bounded broadcast channel; sends to a bounded mpsc (32); writes to WS sink. Three queues bound the worst-case backlog. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-08-01 | DoS (lag amplification) | Lagged log line | mitigate | Per Phase 2 review WR-01: `tracing::warn!(skipped, "..."` — `skipped` is a u64 count, not user-controlled bytes. No log-amplification surface. RESEARCH Security Domain row explicit. |
| T-03-08-02 | DoS (task starvation) | bcast_forwarder spawn | mitigate | One task per connection. Per-connection task count grew from 2 to 3; bounded by the operator's WS connection count (loopback dev tool — typically 1-2 tabs). |
| T-03-08-03 | Race (Hello ordering) | subscribe before Hello | mitigate | Subscribe is called BEFORE `tx.send(Hello)` so any broadcast fired during connection setup is captured. The reader loop running AFTER Hello is also after subscribe — symmetric. |
| T-03-08-04 | Information disclosure | forwarder leaking inbound frames | accept | The forwarder only forwards OUTBOUND (server→client) broadcast frames. Inbound frames go through the unchanged reader loop. No path for client A to see client B's inbound frames. |
| T-03-08-05 | Confused deputy | abort() on bcast_forwarder | accept | `.abort()` is fire-and-forget; the task may run a few more iterations before tokio drops it. Acceptable: it's writing to an already-dropped mpsc (will Err and break naturally) or recv()-blocking (abort interrupts cleanly). |
</threat_model>
