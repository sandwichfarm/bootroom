# Phase 3 — UI Design Contract

> Visual and interaction contract for Phase 3 (Config, Buttons, Watcher) of bootroom.
> Generated by gsd-ui-researcher; verified by gsd-ui-checker.
>
> **This spec INHERITS from `.planning/phases/02-websocket-live-serial/02-UI-SPEC.md` (which itself extends `.planning/phases/01-walking-skeleton/01-UI-SPEC.md`).** The Phase 1 design system, palette, spacing scale, typography roles, and accessibility floor remain authoritative. The Phase 2 button styles (`.hdr-btns button` / `.term-ctrls button` → `--surface` background, `--fg` text, 12px/600 Label, inset `--fg-muted` hover, `--accent` focus ring) are the canonical button styling and are **reused unchanged** for action buttons in this phase. **This document records only the Phase 3 diff.** Where this spec is silent, Phase 2 governs.

**Phase scope reminder (from `03-CONTEXT.md` `<domain>` and `<decisions>`):** add (1) a TOML-driven action-buttons panel between `#hdr` and `#terminal`, (2) a non-intrusive "fresher build available" banner in the same vertical slot, (3) a "config invalid" banner using the existing destructive palette, (4) a new `BUSY` status pill state (input-locked / scenario running — Phase 4 is the first caller; the API and pill ship here so Phase 4 doesn't have to re-architect), and (5) a banner priority ladder so only one banner is visible at a time. The TOML schema, `/api/config` projection, `notify-debouncer-full` wiring, and new `WsMessage` variants are implementation concerns of the planner/executor and do not surface new visual elements beyond what is described here.

**Aesthetic anchor (unchanged):** developer test harness, terminal-adjacent, dense, no chrome. Action buttons must read as *part of the page chrome*, not as a SaaS toolbar — same `LAUNCH`/`RESET` treatment from Phase 2 applies. Banners must read as *terse status lines*, not as notifications/toasts.

### BUSY pill color decision

**Decision: `BUSY` reuses `--fg-muted` (`#7A8295`) — no new palette entry; visually identical to `IDLE`.**

Rationale:
- The pill text is the load-bearing carrier of state, not the background color. Per the Phase 1 accessibility floor, "color is not the sole carrier of status": the literal text `IDLE` vs `BUSY` discriminates the two states unambiguously.
- `BUSY` is a transient state ("input locked because a scenario is executing"). It is *not* destructive or alarming — destructive red is reserved for `HALTED` and for the two error banners. Reusing `--fg-muted` keeps the palette at 10 colors.
- Phase 4 is the first caller of `funnel.lockInput()` / `unlockInput()`; the pill change is one of three feedback channels (the pill, the locked terminal cursor, and the disabled action buttons). The palette does not need to scream.
- `--status-loading` (amber) was considered and rejected: LOADING already means "qemu-wasm worker is instantiating" — overloading amber to also mean "scenario running" would conflate two distinct semantics.
- Contrast: identical pair to IDLE (text `--fg` `#C0CAF5` on background `--fg-muted` `#7A8295` — must reach WCAG AA 4.5:1; if it falls short, executor uses `--bg` `#0E1116` as text color, matching whatever the IDLE pill ended up using after the Phase 2 contrast check). Whatever IDLE shipped with is what BUSY ships with — they MUST use identical text/background pair to avoid an inconsistency.

### Accent reservation (Phase 3 amendment — one new use)

Accent (`--accent`) is reserved EXCLUSIVELY for:
1. The "bootroom" wordmark (header, top-left).
2. The `sha256` field value (12-char prefix in the header).
3. The 1px focus ring on all buttons (Phase 2 addition — Launch/Reset/Clear/Copy and Phase 3 action buttons inherit unchanged).
4. **NEW in Phase 3:** the inline `LAUNCH` button text color *inside* `#fresh-banner` — and **only** inside the fresh-kernel banner. Rationale: the fresh-banner's purpose is "press this one button to load the freshest kernel" — the core value proposition of the product per `CLAUDE.md`. Accent-coloring the LAUNCH text makes it the single visually-loudest control on the page when the banner is shown, which is the desired hierarchy in that moment. The dismiss `×` next to it uses `--fg-muted` to read as secondary.

**Strict NOT-uses (unchanged):** accent is still NOT used for action button fill / text / hover, the top-bar Phase 2 LAUNCH/RESET buttons, status pill backgrounds, the config-invalid banner, or the action-groups label color. The fresh-banner inline LAUNCH text is the one and only Phase 3 amendment to the reservation.

### Banner background decision

**Decision: `#fresh-banner` uses `--surface` (neutral); `#config-banner` uses `--banner-bg` (destructive red).**

Rationale:
- The fresh-kernel banner is *informational and dismissable* — "a new build is available, here's a one-click loader." It must read as non-intrusive (per `03-CONTEXT.md` `<decisions>`: "non-intrusive 'fresher build available' banner"). `--surface` is the same neutral background used by the header and Phase 2 buttons; the banner reads as an extension of the page chrome.
- The config-invalid banner is *an error state* — the user's config is broken and the UI is using the last-known-good config. It MUST read as a problem; reusing `--banner-bg` (destructive red, already used by `#iso-banner`) places it in the same visual register as the existing iso-banner. The two destructive banners (iso and config-invalid) are mutually exclusive per the priority ladder, so the user never sees two red surfaces stacked.
- No new banner-neutral background token is introduced. `--surface` is sufficient.

### Action button hover state (inherited)

Action buttons inside `#actions-panel` reuse the Phase 2 button hover treatment **unchanged**:
- Resting: `background: var(--surface)`, text `var(--fg)`.
- Hover: same background, plus an inset 1px top border in `var(--fg-muted)` (the Phase 2 "lift" effect).
- Active: same as resting (flat aesthetic).
- Focus-visible: 1px outline in `var(--accent)`, `outline-offset: 1px`.
- Disabled (when `BUSY` pill is active — i.e., funnel is input-locked): text → `var(--fg-muted)`, background → `var(--surface)`, cursor `not-allowed`.

No new CSS rules required for action buttons themselves beyond reusing the existing `.hdr-btns button` / `.term-ctrls button` selector list (or, per Phase 2's executor-discretion note, the consolidated `.btn-mono` class if the executor chose to factor it).

**Tone:** unchanged from Phase 1+2. Terse, technical, present-tense, no exclamation marks, no emoji. The two new banners are statements of fact, not calls to action ("Kernel rebuilt —", "bootroom.toml is invalid"). The inline LAUNCH and dismiss `×` ARE the calls to action.

**Destructive-action audit (per template):** Phase 3 introduces no actions that bootroom itself classifies as destructive. User-authored actions may send arbitrary bytes (including `\x03\x03\x03` Ctrl-C × 3 or `reboot\r`), but those are user intent expressed in TOML — bootroom is a pass-through. The harness's no-confirmation policy is documented and unchanged.

## Interaction Contracts (Phase 3)

Phase 1's five contracts and Phase 2's eight remain. Phase 3 adds the following and amends two:

### Amended from Phase 2

- **(amend) Status pill state machine.** Phase 2's four states (`IDLE` / `LOADING` / `RUNNING` / `HALTED`) become five. `BUSY` is added. Transitions:
  | State | Trigger |
  |-------|---------|
  | `BUSY` | `funnel.locked === true` (set by `funnel.lockInput()`). Overrides the locally-derived RUNNING/IDLE/etc. but does NOT override `HALTED` (a halted guest is not busy — it's stopped). |
  | (back to prior state) | `funnel.unlockInput()` re-evaluates `recomputePillLocal()` and restores LOADING/RUNNING/IDLE per the Phase 2 state machine. If a server WS `State` arrived during the lock window, it takes precedence. |
  Phase 3 ships the API + pill but does NOT call `lockInput()` itself — Phase 4 (scenario engine) is the first caller. The pill is exercised by a manual JS-console test in Phase 3 (executor task), not by an end-to-end scenario.
- **(amend) Keyboard input + action button clicks.** Both routes through the funnel. When `funnel.locked === true`:
  - `xterm.onData` callback short-circuits BEFORE `funnel.enqueue` — keystrokes are dropped silently (no visual feedback in the terminal; the BUSY pill is the only signal).
  - Action button click handlers ALSO short-circuit; clicks are no-ops while locked. Buttons render with the `disabled` attribute via the JS state machine when `funnel.locked === true` so they read as not-clickable.
  - Server-initiated `WsMessage::SerialIn` STILL flows through to the funnel — the lock excludes user-initiated input only. This matches `03-CONTEXT.md` `<decisions>` "Funnel input lock primitive."

### New in Phase 3

1. **Action button click handler.**
   1. If `funnel.locked === true`, no-op (see amended contract above).
   2. Read the action's pre-decoded bytes from the rendered DOM data-attribute (server has already base64-decoded the TOML `bytes` field's escape sequences once during `LoadedConfig::load` — the client receives a base64 payload and `atob`'s it to a `Uint8Array`).
   3. `funnel.enqueue(bytes, { pacingMs: 15 })` — uses the global Phase-2 default. Per-action pacing override is `<deferred>`.
   4. No status pill change (server may push State if it observes the resulting guest behavior).
   5. No WS round-trip — the click bypasses the server entirely and writes directly through the existing client funnel. (Per `03-CONTEXT.md` `<decisions>` "Action invocation flow — direct client funnel".)
2. **Banner priority resolver (load-bearing JS logic — must be implemented).** A single `resolveBanners()` function runs on any state change that could affect banner visibility (initial `GET /api/config`, every WS `KernelChanged` / `ConfigUpdate` / `ConfigInvalid`, dismiss-click, and inline-LAUNCH-click). It enforces the ladder:
   | Priority | Banner | Shows when | Hides when |
   |----------|--------|------------|------------|
   | 1 (highest) | `#iso-banner` | `crossOriginIsolated === false` at page load | Never (informational, no dismiss — Phase 1 contract). While shown, both Phase-3 banners are forced hidden. |
   | 2 | `#config-banner` | Most recent WS frame for config was `ConfigInvalid` AND `#iso-banner` is hidden | Next `ConfigUpdate` arrives (no dismiss). While shown, `#fresh-banner` is forced hidden. |
   | 3 (lowest) | `#fresh-banner` | Most recent WS `KernelChanged` was unacknowledged AND priorities 1 + 2 hidden | User clicks the inline LAUNCH (page reload removes the banner incidentally) OR clicks dismiss `×` (sets `hidden`). |
   - "Forced hidden" means the resolver explicitly sets the `hidden` attribute on lower-priority banners when a higher-priority one is shown — they do NOT auto-show when the higher one dismisses unless the underlying state still says they should.
   - The resolver runs synchronously after every state mutation — there is no animation, no transition. Banners snap in and out.
3. **Initial config load on page boot.** After WS `Hello` is received and BEFORE `bootGuest()` runs, the client issues `GET /api/config` and renders `#actions-panel`. If the request fails (4xx/5xx), `#actions-panel` stays hidden and a single `[bootroom] config unavailable: <status>` line is written to the terminal. The page is still usable — Launch/Reset still work, the terminal still mounts. (This is a "no zero-state" continuation of the Phase 1+2 philosophy: missing config is not a blocker for the always-available manual controls.)
4. **WS `ConfigUpdate` handler.** Replace the current rendered action buttons in place: `actionsPanel.replaceChildren(...buildFromConfig(config))`. Re-show `#actions-panel` if it was hidden, hide it if `config.actions.length === 0`. Run `resolveBanners()` (this also auto-hides `#config-banner` if previously shown). Write `[bootroom] config reloaded (<N> actions, <M> scenarios)` to the terminal.
5. **WS `ConfigInvalid` handler.** Set `#config-banner` body to the error message (+ line/col if present), set the state flag the resolver reads, run `resolveBanners()`. Do NOT touch `#actions-panel` — the last-known-good actions remain clickable.
6. **WS `KernelChanged` handler.** Set `#fresh-banner` content to the success or warning variant based on `ok`, set the state flag the resolver reads, run `resolveBanners()`. Do NOT auto-reload the page — the user MUST click LAUNCH (per `WCH-05` and `03-CONTEXT.md` `<decisions>`).
7. **Fresh-banner inline LAUNCH click.** Identical handler to the header LAUNCH button (Phase 2 contract #2): disable both header LAUNCH and the inline LAUNCH, send `WsMessage::Launch`, `requestAnimationFrame` → `window.location.reload()`. The banner stays visible during the reload animation frame; the reload removes it.
8. **Fresh-banner dismiss click.** Set `#fresh-banner` `hidden = true`. Do NOT clear the "pending kernel change" state — if a NEW `KernelChanged` arrives, the banner re-shows. The dismiss is per-event, not a persistent preference.
9. **Funnel lock API surface (ships in Phase 3, exercised by Phase 4).**
   - `funnel.lockInput()`: sets `funnel.locked = true`, sets pill `data-state="BUSY"`, sets `disabled` on every `.action-btn` element. Idempotent.
   - `funnel.unlockInput()`: clears `funnel.locked`, re-runs `recomputePillLocal()` (Phase 2 function), removes `disabled` from every `.action-btn`. Idempotent.
   - Phase 3 manual test (executor task, not Phase 4): paste `funnel.lockInput()` into the DevTools console with a config that has actions; confirm pill flips to BUSY and buttons render disabled; confirm `unlockInput()` reverses both.
10. **`bootroom check` and `bootroom init` are CLI-only surfaces.** They write to stdout/stderr per the Copywriting Contract above. They do NOT have a UI surface — there is no "Check config" button in the browser. The user runs them in a terminal as preflight steps.

### Explicitly NOT in Phase 3

- No animation / transition on banner show/hide (snap, terminal aesthetic).
- No animation on action panel re-render — `replaceChildren` is synchronous + flat.
- No icons on action buttons (text label only; user authors the label in TOML).
- No confirmation dialog for any action button (per `<deferred>`).
- No per-action keyboard shortcuts (v2, per FEATURES.md "Should have").
- No drag-to-reorder action groups (insertion order is TOML order; users edit the file).
- No tooltips on action buttons. If TOML provides `description`, Phase 3 does NOT render it — `description` is reserved for `bootroom check`'s `--verbose` output and future help surfaces. Rendering descriptions as tooltips would compete with the no-modals/no-chrome aesthetic; defer until users ask.
- No banner stacking — only one banner visible at a time per the priority ladder.
- No "remember dismiss" across reloads — fresh-banner dismiss is per-event.
- No light-mode / theme toggle (still deferred since Phase 1).

## Accessibility Floor (Phase 3 deltas)

Phase 1+2 contracts hold. Additions:

- `#actions-panel` is `<div>` (not `<nav>` or `<menu>`) — it is content, not navigation. The `.action-group` containers carry the visible group label as a `<span>`, NOT a heading element, to avoid injecting `<h2>`/`<h3>` into a page that has none. If a future audit calls for semantic group headings, a non-visual `<h2 class="visually-hidden">` may be added without changing visuals.
- Every action button is a real `<button>` element with text content; no `aria-label` needed (the visible text IS the accessible name).
- The fresh-banner dismiss button is `<button aria-label="Dismiss">×</button>` — the `×` character is decorative; screen readers should announce "Dismiss". The inline LAUNCH button has no `aria-label` (text content suffices).
- `#config-banner` has `role="alert"` so assistive tech announces it on un-hide (same pattern as `#iso-banner`).
- `#fresh-banner` does NOT use `role="alert"` — it is informational, not an interruption. Assistive tech announces it via normal DOM-update flow when it appears in the live region inherited from the page (xterm output region is separate).
- The `BUSY` pill text is real text (same pattern as IDLE / LOADING / RUNNING / HALTED — color is not the sole carrier of state). Screen readers will announce the pill text on state change because the `data-state` attribute toggle re-evaluates the element.
- Disabled action buttons use the `disabled` attribute (not just CSS) — assistive tech announces them as disabled, and they're skipped during Tab focus traversal.
- Contrast verification (executor must validate at implementation time):
  - Action button text `--fg` on `--surface` — same pair as Phase 2 buttons; passes AA per Phase 2 verification.
  - Action-group label `--fg-muted` on `--surface` (the panel background) — expected pass; verify ≥4.5:1 against `#1A1F26` (not `#0E1116`).
  - Fresh-banner body text `--fg` on `--surface` — same pair as above, passes.
  - Fresh-banner inline LAUNCH text `--accent` on `--surface` — `#7AA2F7` on `#1A1F26`, verify ≥4.5:1 (expected ≈7:1).
  - Fresh-banner dismiss `×` text `--fg-muted` on `--surface` — `#7A8295` on `#1A1F26`, verify ≥4.5:1 (this is borderline — if it fails, fall back to `--fg` and rely on the absence of accent to read as secondary).
  - `BUSY` pill — uses the IDLE pair, inherits IDLE's verification result.
- Tab order: Phase 2 buttons → action buttons (in TOML order, group-by-group) → terminal → terminal controls → (any visible banner buttons). The fresh-banner inline LAUNCH and dismiss should be reachable but should NOT be the first focusable element on page load — they only exist when a banner is shown.
