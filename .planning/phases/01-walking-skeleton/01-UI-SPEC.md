# Phase 1 — UI Design Contract

> Visual and interaction contract for Phase 1 (Walking Skeleton) of bootroom.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase scope reminder (from CONTEXT.md `<decisions>` → "Phase 1 UI scope"):** kernel-info header, status pill, xterm.js terminal (output-only — no keyboard input wired), and a `crossOriginIsolated` probe banner. Nothing else. Launch / Reset / Clear / Copy / action buttons / scenario UI are deferred to Phase 2+.

**Aesthetic anchor:** developer test harness, terminal-adjacent, dense, no chrome. Reference point is GDB's web UI or a Buildbot console view — *not* a SaaS dashboard. The browser tab is a debugging surface, not a product.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable (vanilla HTML + ES modules, no bundler — project constraint) |
| Component library | none (hand-authored HTML elements styled with a single embedded CSS file at `crates/bootroom/web/style.css`) |
| Icon library | none (Phase 1 has zero icons — status pill uses a colored Unicode disc `●`, banner uses no icons; no SVG asset spend) |
| Font | System monospace stack: `ui-monospace, "SF Mono", "Cascadia Mono", "Menlo", "Consolas", "Liberation Mono", monospace` for the entire page, including header (no proportional font anywhere in Phase 1). xterm.js inherits and ships its own monospace metrics. |

**Rationale for "no design system":** Project CLAUDE.md forbids an npm-based frontend toolchain. shadcn is a React-only initializer and requires Tailwind + a bundler — incompatible. The Phase 1 UI surface (≤4 elements + xterm widget) is well below the threshold where a component library is worth paying for; a single hand-written `style.css` (target ≤150 LOC) is the right tool.

## Spacing Scale

Declared values (multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline padding inside the status pill, gap between header field label and value |
| sm | 8px | Vertical gap between header rows; horizontal gap between adjacent header fields |
| md | 16px | Page outer padding (body padding); gap between header block and terminal; gap between probe banner and content below it |
| lg | 24px | (Reserved — not used in Phase 1; declared so Phase 2's button rows have a consistent token) |

Exceptions: none. Phase 1 uses xs / sm / md only. The terminal fills remaining viewport with no internal padding (xterm.js manages its own canvas).

---

## Typography

Phase 1 uses **two sizes and two weights** — the page is dense, glanceable, monospace-only. No proportional fonts, no heading hierarchy beyond the header itself being slightly larger than the body fields.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / kernel-info value | 13px | 400 (regular) | 1.5 |
| Label (header field name, status pill text, banner text) | 12px | 600 (semibold) | 1.4 |
| Header title ("bootroom" wordmark, top-left) | 14px | 600 (semibold) | 1.2 |
| Terminal | xterm.js default (14px monospace, managed by the widget) | n/a | n/a |

Weight policy: exactly two weights — 400 and 600. No italic. No underline anywhere (links are not part of Phase 1).

Letter spacing: default for all roles. The status pill text uses `text-transform: uppercase` and `letter-spacing: 0.05em` to read as a state badge rather than free-form text.

## Color

Single dark theme for Phase 1. No light-mode toggle (deferred). Palette is intentionally narrow — three neutrals plus three semantic colors. All values are CSS-named or hex; no opacity tricks.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0E1116` | Page background, terminal background (xterm.js theme override). The entire viewport reads as a single dark surface. |
| Secondary (30%) | `#1A1F26` | Header strip background (top of viewport); probe banner background when shown; status pill background. These are the only "card-like" surfaces in Phase 1. |
| Accent (10%) | `#7AA2F7` (soft blue) | **Reserved exclusively for:** (1) the "bootroom" wordmark in the header, (2) the `sha256_prefix` field value (the only header field rendered in accent — signals "this is the identity hash"). Nothing else. |
| Foreground (text) | `#C0CAF5` | Default text color for header labels, header values, banner text |
| Muted foreground | `#7A8295` | Header field labels (`path`, `size`, `mtime`, `sha256`) — distinguishes label from value at a glance |
| Status — Loading (info) | `#E0AF68` (amber) | Status pill background while qemu-wasm Worker is instantiating |
| Status — Running (success) | `#9ECE6A` (green) | Status pill background once `crossOriginIsolated` is true AND the Worker has reported boot |
| Status — Halted (destructive) | `#F7768E` (red) | Status pill background when the Worker has exited or signaled halt |
| Probe banner background (error) | `#3B1F26` | Background of the `crossOriginIsolated` probe banner when SAB is unavailable. Foreground text on banner is `#F7768E` semibold for the headline, `#C0CAF5` regular for the body. |

**Accent reserved for:** the "bootroom" wordmark, and the `sha256` field's value. Two surfaces. That's it. Specifically NOT used for: status pills (they have their own semantic colors), banner (uses destructive red), header labels, or any future interactive control.

**Contrast verification (must be checked at implementation time):**
- `#C0CAF5` on `#0E1116` → ratio ≈ 13.7:1 (passes WCAG AAA for normal text)
- `#7A8295` on `#0E1116` → ratio ≈ 5.6:1 (passes WCAG AA for normal text — sufficient for muted labels)
- `#7AA2F7` on `#0E1116` → ratio ≈ 8.0:1 (passes AAA)
- Status colors on `#1A1F26` pill background — all three pass AA (≥4.5:1) for the 12px semibold pill text; planner/executor must verify with a contrast checker on the final pixels.

## Copywriting Contract

Phase 1 has **no buttons, no destructive actions, no forms, and no scenario interactions**. The copy surface is the header field labels, the status pill states, the probe banner, and a single stdout line printed by the binary itself when `bootroom serve` starts.

| Element | Copy |
|---------|------|
| Primary CTA | **none in Phase 1.** The only user action is "open the URL printed by `bootroom serve`." A Phase 2 placeholder is *not* rendered. |
| Empty state heading | **n/a** — there is no empty state. `--kernel` is a required CLI flag; if absent, `bootroom serve` exits with a clap error before the page is reachable. The page always has a kernel to describe. |
| Empty state body | n/a (see above) |
| Error state — `crossOriginIsolated` probe banner headline | `Cross-origin isolation is not active.` |
| Error state — probe banner body | `Bootroom requires COOP: same-origin and COEP: require-corp on every response. Open DevTools → Network and inspect the response headers on this page.` |
| Error state — kernel fetch failure (xterm renders `Failed to load kernel` into terminal output, not a UI surface) | `Failed to load kernel from /kernel: <HTTP status>. Check that bootroom is still running and that the kernel file at <path> is readable.` (rendered into the terminal as plain text on a single line, prefixed `[bootroom]`) |
| Destructive confirmation | **none in Phase 1.** No destructive actions exist. |
| Status pill — Loading | `LOADING` (uppercase, semibold, 12px — see Typography) |
| Status pill — Running | `RUNNING` |
| Status pill — Halted | `HALTED` |
| Header field labels (exact strings, lowercased, no punctuation) | `path` `size` `mtime` `sha256` |
| Header field value — `size` | Human-readable: `12.4 MiB` (use IEC binary units: KiB / MiB / GiB; one decimal place when ≥10, two below). Raw byte count is in the JSON response but not rendered. |
| Header field value — `mtime` | ISO-8601 local timezone, second precision: `2026-05-17T14:32:08-07:00`. Not "5 minutes ago" — a test harness wants exact timestamps. |
| Header field value — `sha256` | First 12 hex chars, lowercase, accent-colored: `a3f29b4c1e08`. The full hash is in the JSON response; the header shows the prefix only (mirrors `git rev-parse --short`). |
| Header field value — `path` | Render verbatim as supplied to `--kernel`. Do not truncate, do not resolve symlinks. If wider than the viewport, allow horizontal overflow on the field with `overflow-x: auto` rather than ellipsizing — the user needs to see the full path. |
| Page `<title>` | `bootroom — <kernel basename>` (e.g., `bootroom — Image`). Allows tab-switching to identify which kernel is in which tab. |
| Wordmark text (top-left of header) | `bootroom` (lowercase, semibold, accent color). No tagline, no version string in Phase 1. |
| Server stdout line on start (CLI, not UI — included here because it's user-facing copy in this phase) | `Serving bootroom on http://127.0.0.1:8765 (Ctrl-C to stop)` (from CONTEXT.md `<decisions>`, included verbatim for completeness). |

**Tone:** terse, technical, present-tense. No exclamation marks. No emoji. No "Welcome" / "Hello" / "Get started" copy — the user is already started. Error messages always include both what failed and where to look next (banner body demonstrates this pattern).

## Interaction Contracts (Phase 1)

Phase 1 has no interactive controls. The interactions that DO exist are state observations:

1. **Page load → fetch kernel info.** On `DOMContentLoaded`, JS issues `GET /api/kernel/info`. On 2xx, populate the four header fields. On non-2xx or network error, render `ERR` in each field value (muted-foreground color) and log to console — the page must not crash. The status pill stays `LOADING`.
2. **Page load → SAB probe.** Synchronously inline at the very top of `<body>` (before module scripts), check `crossOriginIsolated && typeof SharedArrayBuffer !== 'undefined'`. If false: un-`hidden` the banner. This check runs FIRST so the banner is visible even if emscripten initialization fails downstream.
3. **emscripten lifecycle → status pill.** The qemu-wasm loader (per `qemu-wasm/examples/riscv64/src/htdocs/index.html`) exposes `Module.onRuntimeInitialized`, `Module.onExit`, `Module.onAbort`. JS subscribes to all three: `onRuntimeInitialized` → transition pill to `RUNNING`; `onExit` or `onAbort` → transition pill to `HALTED`. No other states exist in Phase 1.
4. **xterm.js mount.** Per reference wiring: `openpty()` → mount `master` addon on `Terminal` → `Module.pty = slave`. Serial bytes from the guest will render in the terminal automatically via xterm-pty. No bootroom code touches `slave.write` in Phase 1.
5. **Window resize.** xterm.js's `FitAddon` is loaded and called on `resize` events. Header layout reflows via CSS flex-wrap.

Explicitly NOT in Phase 1: no `/ws` connection, no `EventSource`, no `POST`, no keyboard wiring, no copy/paste handlers beyond the browser default, no focus management.

## Accessibility Floor

- `<header>` uses semantic `<header>` element, `<dl>` for the kernel info pairs.
- Probe banner has `role="alert"` so assistive tech announces it when un-hidden.
- Status pill text is real text inside the `<span>` (not background-image) — screen readers will read `LOADING` / `RUNNING` / `HALTED`. The leading `●` glyph is wrapped in `<span aria-hidden="true">`.
- Color is not the sole carrier of status: the pill text (`LOADING` / `RUNNING` / `HALTED`) carries the information independently of the background color.
- All text meets WCAG AA contrast (4.5:1) on its background per the verification list above.
- xterm.js accessibility is whatever upstream ships in 5.3.0 — bootroom does not regress it. Do not set `aria-hidden` on the terminal container.

## Open Questions Deferred to Phase 2+

- Light-mode / theme toggle — not in Phase 1.
- Header collapse on narrow viewports — Phase 1 wraps; a more sophisticated responsive treatment lands when Phase 2 adds Launch/Reset.
- Status pill `Idle` state — UI-06 requires `Idle / Loading / Running / Halted`, but `Idle` only makes sense once Launch/Reset exist (Phase 2). Phase 1 starts in `Loading` and never returns to a pre-boot state.
- Banner dismissal — Phase 1 has no dismiss control; the banner is informational and reflects ground-truth state. If the user fixes their reverse-proxy and refreshes, the banner is gone.
