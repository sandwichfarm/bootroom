<interfaces>
What plan 01-06 already established about Module.FS:
- The Phase 1 boot path uses `Module.preRun.push(...)` with `Module.FS.writeFile('/pack/Image', bytes)` BEFORE `initEmscriptenModule` runs. So we already know that "writing into Module.FS at the preload phase" works.
- The open question (Spike A's actual question) is whether writing to `/pack/Image` AFTER the guest has booted, then resetting the guest, picks up the new bytes — without re-running emscripten's pack-builder.

What this spike needs:
- Two distinguishable kernel variants:
  - Variant A: emits a recognizable banner on boot (e.g., a kernel printing `BOOTROOM-SPIKE-A-VARIANT-A`).
  - Variant B: emits a different banner (e.g., `BOOTROOM-SPIKE-A-VARIANT-B`).
  - Real kernels are expensive to produce; the spike can fall back to "the kernel that was used in Spike B" + "a corrupted copy that should cause Module.onAbort with a different error message" if no second real variant is available. The signal we need is just "the swap took effect" — distinguishable by ANY observable change in behavior.

What the spike does NOT test:
- The bytes-on-the-wire protocol (Phase 2 / `/ws`).
- The UX of the Launch button (Phase 2 plan).
- The TOML config or watcher (Phase 3).

The spike uses the running bootroom server from plan 01-04+05 — we serve two `/kernel?variant=<a|b>` endpoints via a custom query parameter handler the spike's scaffolding wires up locally, OR we run two bootroom processes on different ports each with its own `--kernel`. The latter is simpler and matches Phase 1's surface (no Phase 2 multi-kernel switching).

    Per CONTEXT.md decision: confirm whether the browser can swap the kernel

      - `fixtures/Image-B` — second variant. Easiest options:

        - The same kernel but with a deliberately corrupted first byte; this

    Authored to be pasted into the DevTools console of the running Phase 1 page:

    ```javascript
    // Spike A swap probe — paste into DevTools console of a running bootroom
    // page (http://127.0.0.1:8765/) after the guest has reached RUNNING.

    (async function() {
      // CONFIGURE: where to fetch the second kernel from. Examples:
      //   '/kernel' (no-op — same kernel; just tests the writeFile path)
      //   'http://127.0.0.1:8766/kernel' (a second bootroom on a different port)
      //   'fixtures/Image-B' (if served from --assets-dir)
      const KERNEL_URL = '/kernel';

      console.group('[spike-a]');
      console.log('Pre-swap pill state:', document.getElementById('status')?.dataset?.state);
      console.log('Module exists:', typeof Module !== 'undefined');
      console.log('Module.FS exists:', typeof Module !== 'undefined' && !!Module.FS);

      if (typeof Module === 'undefined' || !Module.FS) {
        console.error('Module.FS not reachable; spike cannot proceed. Confirm guest reached RUNNING first.');
        console.groupEnd();
        return { verdict: 'red', reason: 'Module.FS not available post-boot' };
      }

      // Snapshot existing /pack/Image
      let preBytes;
      try {
        preBytes = Module.FS.readFile('/pack/Image');
        console.log('Pre /pack/Image size:', preBytes.length, 'sha first 8:', preBytes.slice(0, 8));
      } catch (e) {
        console.warn('Could not readFile /pack/Image:', e.message);
      }

      // Fetch the candidate replacement
      console.log('Fetching new kernel from', KERNEL_URL);
      const res = await fetch(KERNEL_URL);
      if (!res.ok) {
        console.error('Fetch failed:', res.status);
        console.groupEnd();
        return { verdict: 'red', reason: 'kernel fetch failed' };
      }
      const newBytes = new Uint8Array(await res.arrayBuffer());
      console.log('New kernel size:', newBytes.length);

      // Attempt the writeFile
      let writeOk = false;
      try {
        Module.FS.writeFile('/pack/Image', newBytes);
        writeOk = true;
        const postBytes = Module.FS.readFile('/pack/Image');
        console.log('Post /pack/Image size:', postBytes.length,
          'matches:', postBytes.length === newBytes.length);
      } catch (e) {
        console.error('writeFile failed:', e.message);
        console.groupEnd();
        return { verdict: 'red', reason: 'writeFile rejected: ' + e.message };
      }

      // The write succeeded. Now the harder question: does the running QEMU
      // pick this up? QEMU doesn't re-read /pack/Image after the initial -kernel
      // load, so we need a guest reset.
      //
      // Options to trigger reset (in order of preference):
      // 1. Use QEMU's qmp/monitor — qemu-wasm may not expose this.
      // 2. Call Module._qemu_system_reset() or similar exported symbol if available.
      // 3. Full page reload — works but defeats "no page reload" goal.
      //
      // Probe option 2:
      const resetFns = Object.keys(Module).filter(k =>
        k.toLowerCase().includes('reset') || k.toLowerCase().includes('reboot')
      );
      console.log('Reset-like exports in Module:', resetFns);

      // If nothing usable, attempt option 3 documented for the result.
      console.log('writeFile path: WORKS. Reset path: ', resetFns.length > 0 ? 'POSSIBLY VIA ' + resetFns.join(', ') : 'NOT FOUND — page reload required');
      console.log('Manual verdict input:');
      console.log('  green if you call one of the reset fns and see variant B boot');
      console.log('  amber if writeFile works but no in-place reset path exists');
      console.log('  red if writeFile itself fails or corrupts state');
      console.groupEnd();
      return { writeOk, resetFns, preLen: preBytes?.length, newLen: newBytes.length };
    })();
    ```
