<threat_model>
## Trust Boundaries

Phase 4 widens the `/ws` protocol surface. No new external input is parsed in this plan (all new variants are constructed server-side or by the trusted browser engine in 04-08). The deny_unknown_fields omission is a deliberate Phase-2 design that survives every additive change.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01-01 | Tampering | A client sending `ScenarioResult` with arbitrary `actions` / `transcript` JSON in `serve` mode | accept | `serde_json::Value` accepts any JSON. The downstream consumer is `ws.rs::handle_wire` (04-05), which checks for an awaiting `oneshot` and logs-and-continues if none (warn-only); the file's only use of the payload is byte-forwarding to `--log-file` (operator-owned). No path interprets the opaque values. |
| T-04-01-02 | DoS | Oversized `transcript` / `actions` payloads on the WS path | accept | axum WS default frame size is multi-MB; CR-02 origin allow-list (Phase 3) restricts senders to same-origin loopback. The `ws.rs` reader (Phase 3) already truncates bad-JSON warn logs at 256 bytes (`truncate_for_log`); a malformed-but-parseable oversized frame is funneled to the oneshot consumer in 04-07 which sets an outer timeout. No new mitigation needed at the type level. |
| T-04-01-03 | Info disclosure | `transcript` field in WS frames contains base64-encoded kernel serial output | accept | `transcript` is browser-built, server-forwarded. Same operator trust model as `--kernel`. WS is loopback-only (`--host 127.0.0.1` default; CR-02 origin allow-list). No new exposure beyond Phase 2's `SerialOut` mirror. |
</threat_model>
