<objective>
Add a `scenario_result_tx` slot on `AppState` so the `bootroom run` driver (04-07) can install a oneshot sender BEFORE launching Chromium, and the `/ws` handler (04-05) can take and fire that sender when a `ScenarioResult` frame arrives from the browser.

The field is `Arc<Mutex<Option<oneshot::Sender<WsMessage>>>>` because:
- `oneshot::Sender::send` consumes `self` by value — must be `take()`-able out of the Option.
- `tokio::sync::Mutex` (NOT `std::sync::Mutex`) because the WS handler holds the mutex across an `.await` point (`tx.send(...)` doesn't actually `await`, but the surrounding code does).
- `Arc<…>` so `AppState: Clone` continues to hold; the per-request `State<Arc<AppState>>` extractor in axum needs Clone.

Purpose: Decouple the runtime mode (serve vs run) from the type. `serve` mode leaves the Option `None`; `run` mode installs a `Some(tx)` exactly once at process startup. The take-once semantics prevent two scenarios from concurrently competing for the same oneshot (`bootroom run` is one-scenario-per-invocation by contract).

Output: `AppState` carries the new field; all Phase 2/3 tests still pass; new unit tests pin the take-once semantics.
</objective>

<threat_model>
## Trust Boundaries

The new field is purely server-internal; no external input flows through `scenario_result_tx`. The mutex is held only across non-await work (`take()` is non-blocking once the lock is acquired). The `WsMessage` payload that flows through the oneshot is the `ScenarioResult` enum variant from 04-01, validated as well-formed JSON by serde at the WS layer (Phase 2).

## STRIDE Threat Register

| T-04-04-01 | DoS | A malicious client in `serve` mode sends repeated `ScenarioResult` frames hoping to leak server state | accept | `take_scenario_result_tx` returns `None` in serve mode (no installer). The WS handler in 04-05 logs-and-continues. No state mutation; no resource exhaustion (warn-logs are truncated by Phase 3's `truncate_for_log`). |

The `Mutex` serializes any racing install; the explicit "second install replaces first" semantics is unit-tested. There is no client-driven install path. |
| T-04-04-03 | Spoofing | A `serve`-mode client sends `ScenarioResult` to forge a verdict somewhere | accept | No verdict-acceptance path exists outside `run_cmd`. The oneshot is `None` in serve mode; the handler discards the frame. |
