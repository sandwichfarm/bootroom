<objective>
Extend Phase 3's `LoadedConfig::from_config` to compile-check every `kind = "regex"` assertion pattern at load time using the Rust `regex` crate. Surface compile failures as `LoadError` with the scenario name, the `after` label, and the offending pattern. Promote `regex` from transitive (already in `Cargo.lock`) to a direct `bootroom-core` dependency.

Purpose: Fail fast in `bootroom check` and `bootroom serve` BEFORE the browser engine (04-08) attempts to compile the same pattern as JS `RegExp` at runtime. The Rust engine is strictly stricter for backreferences and lookaround (Pitfall #1 in 04-RESEARCH), so a Rust-side compile-check is the canonical pre-flight: anything Rust accepts, JS `RegExp` also accepts.

Output: `bootroom-core` exports unchanged `LoadedConfig` surface, but rejection of invalid regex now happens at load time. The Rust∩JS feature subset is documented inline.
</objective>

    ```rust
    // Phase 4 RUN-04 / RUN-05: compile-check every `kind = "regex"`
    // assertion at load time. The browser engine (web/scenario.js) uses
    // JS `RegExp` for runtime matching; the Rust `regex` crate is the
    // STRICTER engine of the two (no backreferences, no lookaround), so
    // anything that compiles in Rust here will also compile as JS
    // RegExp. Inverse: a pattern that uses backref / lookaround is
    // rejected here, which is correct — those features are not
    // portable across the two engines and the supported subset is
    // pinned to Rust regex ∩ ECMAScript RegExp.
    //
    // See 04-RESEARCH Pitfall #1 for the feature-intersection table.
    for s in &cfg.scenarios {
        for a in &s.assertions {
            if matches!(a.kind, AssertionKind::Regex) {
                regex::Regex::new(&a.pattern).map_err(|e| {
                    LoadError::invalid_regex(&s.name, &a.after, &a.pattern, e)
                })?;
            }
        }
    }
    ```

<threat_model>
## Trust Boundaries

`bootroom.toml` is operator-controlled; loaded by `LoadedConfig::load_from_str`. Adding regex compile-check widens the load-time computation surface but the input is already trusted (operator's own file). The only new external library is `regex`.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-02-01 | DoS | Rust `regex` compile of a pathological pattern (e.g., deep nested alternation) | accept | Rust `regex` compile is linear-time per spec; no catastrophic backtracking risk. Match-time is the only DoS surface, and the per-assertion `timeout_ms` (default 5000 ms, enforced by 04-08) is the natural circuit-breaker. |
| T-04-02-02 | Tampering | Misleading scenario / after labels in error messages | accept | `format!("scenario '{scenario}' ...", scenario = s.name)` interpolates operator-controlled strings. Same trust model as the existing duplicate-action / unknown-action-ref error messages (Phase 3). No new exposure. |
| T-04-02-03 | Info disclosure | Regex compile errors include the full offending pattern | accept | The operator's own `bootroom.toml` is the source; surfacing the pattern is the desired diagnostic for `bootroom check`. No PII surface (operator's own config). |
</threat_model>
