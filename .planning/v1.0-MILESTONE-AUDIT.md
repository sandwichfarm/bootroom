## 2. Core Value Check

> "Press one button, get the freshest kernel running in a browser with a click-to-trigger scenario library. Same binary, same assets, same WS protocol, two modes: `serve` (real tab) and `run` (headless CI)."

The loop closes. Three load-bearing facts:

1. **Same router pin.** `crates/bootroom/src/run_cmd.rs:150` calls `bootroom::server::build_router(state)` — the identical Router constructed for `serve` (`server.rs:171`). The contract is pinned by an integration test (`crates/bootroom/tests/run_uses_same_router.rs`).
2. **Real-kernel headless boot.** `crates/bootroom/tests/run_smoke_norn_kernel.rs` (`#[ignore]`-tagged) drives chromiumoxide → headless Chromium → bootroom server → qemu-wasm → NORN kernel → serial banner `[NORN ALLOC] size = 1048576` → ScenarioResult/verdict=pass → exit 0. Verified during Phase-4 verification at 1.29s wall-clock.
3. **Doctor preflight gate.** `bootroom doctor` from `/tmp` reports `overall: pass` on a green install (Phase-5 verification), exits 1 on broken config with a one-line stderr summary naming the failed check. Six checks (version, qemu-wasm rev, browser, COOP/COEP, config, CLI surface).

Operationally, an external kernel CI workflow can today install `bootroom` from a `cargo install --git` source build, run `bootroom doctor` as a preflight, and `bootroom run --scenario boot_smoke --kernel build/Image` to gate the kernel build. After the maintainer's first manual `cargo publish` (Phase-6 carry-over), the same workflow works from `cargo install --locked bootroom` and `cargo binstall bootroom` against published artifacts.
